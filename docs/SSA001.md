# SSA001 — StringSyntax format mismatch

| Severity | Code fix | Applies with `dotnet format` |
|----------|----------|------------------------------|
| Warning  | No       | No |

Fires when both sides of a flow carry an annotation and their value sets do not overlap. The source is declared to be one syntax, the target asks for another.

Value sets match on **overlap**, not equality: `[StringSyntax("Json")]` into `[UnionSyntax("Json", "Xml")]` is fine, and two unions pass when their intersection is non-empty. SSA001 fires only when nothing is common to both.


## Example

```cs
public class Target
{
    public void Consume([StringSyntax(StringSyntaxAttribute.Regex)] string value) { }
}

public class Holder
{
    [StringSyntax(StringSyntaxAttribute.DateTimeFormat)]
    public string Value { get; set; }

    public void Use(Target target) => target.Consume(Value);
}
```

Build output:

```
SSA001: property 'Holder.Value' is [StringSyntax("DateTimeFormat")] but flows to parameter 'value' of method 'Target.Consume', which is [StringSyntax("Regex")]. Fix: annotate parameter 'value' of method 'Target.Consume' (line 3) as [StringSyntax("DateTimeFormat")], or pass a value that is [StringSyntax("Regex")].
```

The location in the `Fix:` clause is the *declaration* to edit, which is usually not where the warning is reported — the warning sits at the call, the attribute goes on the declaration. `(line 3)` means the same file as the warning; a declaration elsewhere is given as `(D:\src\Target.cs:3)`. A multi-value side renders as the union it is: `[UnionSyntax("Json", "Xml")]`.


## How to fix

There is **no code fix**, and that is deliberate. Both declarations already carry an annotation, so an automatic fix would have to guess which one is the mistake — and guessing wrong silently launders the bug this rule exists to catch. Pick one:

1. **The target's annotation is wrong.** Change it to the source's syntax.
2. **The source's annotation is wrong.** Change it to the target's syntax.
3. **The wrong value is being passed.** Then SSA001 has found a real bug — pass the value that actually holds the target's syntax.

Do not silence this rule by widening either side to `[UnionSyntax(...)]` or `[StringSyntax("*")]` unless the declaration genuinely accepts both syntaxes. Both are ways to make the warning disappear without answering the question it asked.


## When it does not fire

 * Either side is **Unknown** — a string literal, an interpolated string, a concatenation, an `await`, or any other expression the analyzer can't trace to a declaration. See "Sources the analyzer can resolve" in the readme.
 * Either side is `[StringSyntax("*")]`, the wildcard that accepts any syntax.
 * The value sets overlap on at least one value.
 * The target is `object`, `params object?[]`, or an unannotated generic `T` — a generic value slot that was never going to honour a syntax contract.


## Suppressing

```cs
#pragma warning disable SSA001 // <reason this mismatch is intentional>
```

Prefer fixing over suppressing. If a mismatch really is intentional, say why in the pragma comment — a bare disable is indistinguishable from a bug someone gave up on.
